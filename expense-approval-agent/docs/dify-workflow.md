# Dify 工作流设计

## 当前定位

Dify 负责补充可视化编排，不负责保存 v2 报销系统的最终业务状态。正式演示以 Python 页面和受控 API 为准。

## 节点顺序

1. 开始节点：接收报销字段。
2. LLM 节点：辅助检查用途表达，不做金额或审批判断。
3. 参数校验：缺失字段生成补充清单。
4. 知识检索：检索费用制度，仅用于提供依据。
5. HTTP 请求：调用 `/api/precheck` 兼容接口。
6. 条件分支：按确定性预审结果分流。
7. 人工节点：主管或财务确认。
8. 结果节点：输出结论、原因、下一步和制度来源。

## v2 完整审批为何放在 Python

- 身份必须来自可信登录态，不能由 LLM 或表单自由填写。
- 主管待办需要校验直属关系。
- 预算占用需要事务和并发保护。
- 退回、重提、同意、驳回需要明确状态机。
- 每个动作必须形成不可混淆的审计记录。

## 风险控制

- API 超时或非 JSON 响应不能被描述为“已通过”。
- 模型输出不能修改员工、金额、预算和发票事实。
- API Key 放在环境变量或凭证管理中，不写入 DSL。
- Dify 版本升级后需要重新导入、节点检查和回归测试。
